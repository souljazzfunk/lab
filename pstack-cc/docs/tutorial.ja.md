# チュートリアル: pstack を手を動かして理解する

[English](tutorial.en.md)

pstack の作者 Lauren Tan(poteto)は、使い方を 3 つの資料で説明しています。

- 記事 [The Complete Guide to pstack Pt. 1](https://x.com/poteto/status/2094457600259842065)。検証スキルの話です。
- 記事 [The Complete Guide to pstack Pt. 2](https://x.com/poteto/status/2097732320606507506)。調査、計画、プロトタイプ、設計の話です。
- 講演。エージェントを信頼できるようにする環境づくりの話です。

このチュートリアルでは、資料に出てくるワークフローを自分のリポジトリで 1 つずつ実行します。最後には、自分のアプリ用の検証スキルと、それを使って作った変更が 1 つ手元に残ります。

全体は 3 部に分かれています。第 1 部が Pt. 1、第 2 部が Pt. 2、第 3 部が講演に対応します。1 部あたり 1 時間ほどかかります。部ごとに日を分けても進められます。

## 表記

このチュートリアルでは、スキルを `/how` のように短く書きます。正式な名前は `/pstack:how` です。入力欄で `/how` と打てば、補完の候補に `/pstack:how` が出ます。

`/verify-<app>` は、第 1 部で自分のリポジトリに作る検証スキルです。`<app>` にはアプリの名前が入ります。記事の `/control-app` と同じものです。

プロンプトの中の `<機能>` や `<サブシステム>` は、自分のリポジトリに合わせて書き換えます。

## 準備

1. 普段触っているアプリのリポジトリを 1 つ選びます。ブラウザ、Electron、CLI、API のどれでも構いません。手元で起動できることが条件です。
2. 練習用のブランチを作ります。

    ```bash
    cd <自分のリポジトリ>
    git switch -c pstack-tutorial
    ```

3. 小さな「やりたいこと」を 1 つ決めます。30 分ほどで終わる機能の追加か、再現手順が分かっているバグが向いています。
4. Claude Code を起動し、pstack を入れます。

    ```
    /plugin marketplace add souljazzfunk/lab
    /plugin install pstack@lab
    ```

5. Claude Code を再起動します。`/poteto` と打って、補完に `/pstack:poteto-mode` が出れば準備は終わりです。

モデルの割り当ては既定のままで動きます。変えたくなったときだけ `/setup-pstack` を実行します。

## 第 1 部: エージェントが自分の仕事を確かめられるようにする

Pt. 1 の主張は 1 つです。エージェントが自分の仕事を確かめられないと、人間が確認役になり、ずっと付きっきりになります。第 1 部では、その確認の手段を作ります。

### 1. 検証スキルを作る

```
/create-verification-skill
```

エージェントはまずリポジトリを調べます。アプリの起動方法、操作の方法、証拠の取り方を、コードと README から読み取ります。コードから分からないことだけを質問してきます。

終わると、次のファイルができています。

- `.claude/skills/verify-<app>/SKILL.md`。Launch、Doctor、Drive、Evidence、Cleanup の節があります。
- `.claude/skills/verify-<app>/features/README.md` と、機能ごとのファイルが 3〜5 個。これが Feature Map です。

エージェントは作ったスキルを一度最後まで実行しています。起動、`doctor`、機能を 1 つ操作、証拠の保存、後片付けの順です。返事に、保存したスクリーンショットやログの場所が書かれていることを確かめます。

Claude Code を再起動すると、`/verify-<app>` が補完に出るようになります。

### 2. Feature Map を読む

`features/README.md` を開きます。アプリの主な機能が並び、機能ごとのファイルへリンクしています。

機能のファイルを 1 つ開きます。次の 4 つの見出しがあります。

- `Sub-features`
- `How to get to it (user POV)`
- `Driving it with <harness>`
- `Gotchas`

作者はこれを「形にした記憶」と呼んでいます。ユーザーがどうやってその機能にたどり着くかが書いてあるので、エージェントはアプリを手探りしなくて済みます。記載が間違っていたら、ここで直します。Feature Map はリポジトリに入れて、チーム全員で共有するものです。

### 3. 検証スキルの CLI を触る

pstack の原則「Build the Lever」は、Markdown の説明より道具を渡せ、という意味です。検証スキルの場合、道具はアプリを操作する小さな CLI です。

```
/verify-<app> でアプリを起動し、doctor を実行して、最初の画面のスクリーンショットを撮って
```

エージェントは毎回その場でスクリプトを書くのではなく、スキルに入っている CLI を実行します。返事に、実行したコマンドと、スクリーンショットの保存先が書かれています。

CLI に足りないコマンドがあれば、足してもらいます。Pt. 1 は、エージェント向けの CLI に次の性質を求めています。

```
/poteto-mode verify-<app> の CLI に <足りない操作> のコマンドを足して。詳しい --help を付け、出力は JSON にする。危険な副作用があるなら --dry-run も付ける。エラーメッセージには、代わりに何をすればよいかを書く
```

### 4. 検証付きで機能を作る

準備で決めた「やりたいこと」を、ここで実装します。Pt. 1 のプロンプトをそのまま使います。

```
/poteto-mode <機能> を作って。/verify-<app> で変更を確かめ、証拠として動画かスクリーンショットを見せて
```

エージェントは作業の種類から playbook を選びます。機能の追加なら **Feature**、バグなら **Bug fix** です。最初に todo リストが出て、先頭に playbook の手順が並びます。飛ばす手順も消されず、`skip: <理由>` として残ります。

終わると、返事に次のものが入っています。

- 何を作り、どんなデータの形を選んだか
- 判断に使った原則の名前(Prove It Works など)
- `/verify-<app>` で撮った証拠の場所

証拠を自分の目で確かめます。スクリーンショットが実際の変更を写していなければ、そのことを伝えてやり直させます。

バグを選んだ場合は、Pt. 2 の例 4 のプロンプトを使います。

```
/poteto-mode /verify-<app> でこのバグを再現して。main で再現したら直して、証拠として動画を見せて
```

### 5. `/swarm` で並列に確かめる

`/swarm` は、同じ検証を何体ものエージェントに分担させます。変更で他の機能が壊れていないかを、Feature Map に沿って確かめます。

```
/swarm 4 体で、/verify-<app> を使って features/ の機能を分担して確かめて。今回のブランチで壊れた機能がないかを PASS / ISSUES / BLOCKED で報告して
```

エージェントは worktree を分けて、ワーカーを並列に動かします。最後に、機能ごとの結果の表が 1 つ返ってきます。

Pt. 1 の性能改善の例も、同じ形で書けます。

```
/poteto-mode アプリの初期表示を速くして。まず /verify-<app> で今の状態のトレースを取り、改善できる箇所を探す。次に絞った修正をして、/verify-<app> と /swarm で改善したことを確かめて
```

記事の `/swarm` は Cursor のクラウドで動きます。Claude Code 版は手元のマシンで動くので、同時に動かすのは 5 体までにします。

### 6. 検証スキルを保守する

アプリが変わると、Feature Map はすぐ古くなります。

```
/maintain-verification-skill
```

エージェントは機能ごとにソースを読み、実際にアプリを動かして、Feature Map と食い違う所を探します。結果は `clean`、`changed`、`blocked` のどれかで返ってきます。`changed` なら、直した内容が 1 つの PR にまとまっています。

作者はこれを少なくとも 1 日 1 回実行することを勧めています。検証スキルは重要なインフラとして扱い、当番を決めてもよいくらいだ、とも書いています。

## 第 2 部: 作る前に理解し、コードで計画する

Pt. 2 の主張は 2 つです。エージェントには、良い文脈を渡すほど良い仕事をさせられます。そして、計画は抽象的な文書ではなくコードで立てます。

### 7. 自分の言葉で言い直させる

自分の仮説を先に伝えると、エージェントがそれに引きずられます。そこで、まず問題を言い直させます。題材は、チームに届いたバグ報告や issue、Slack のスレッドです。

```
/poteto-mode この issue を読んで、根本の問題が何だと思うかを、自分の言葉で平易に言い直して
```

返ってきた言い直しを読みます。的外れな点に食いついていたら、コードを書く前のここで直します。

### 8. `/how` と `/why` で仕組みと経緯を調べる

```
/how <サブシステム> はどう実装されている?
```

エージェントは質問の複雑さを判定します。複雑なら探索役を 2〜4 体並列に動かし、1 つの説明にまとめます。見出しは Overview、Key Concepts、How It Works、Where Things Live、Gotchas です。

```
/why なぜ <古い依存や、変わった実装> のままなのか?
```

`/why` は、git の履歴と PR に加えて、Claude Code につながっている MCP を調べます。Slack、Linear、Notion、Sentry などです。つながっていない情報源は飛ばし、飛ばしたことを答えに書きます。答えには、根拠になったコミットや PR が引用されています。

### 9. `/teach` で説明させる

第 1 部で作った変更について、判断の理由を説明させます。

```
/teach 手順 4 の変更を、なぜこの形で実装したのか教えて。ほかの形と比べて何を取り、何を捨てたのか
```

`/teach` は内部で `/how` と `/why` を呼びます。答えは短い説明から始まり、聞くほど深くなります。納得できない点は、そのまま質問を続けます。作者によると、この説明の過程はエージェント自身の理解も正します。

### 10. `/recall` で前回の文脈を戻す

Claude Code を終了して、新しい会話を始めます。前の会話の内容は、新しい会話には残っていません。

```
/recall 昨日やった <機能> の作業を思い出して
```

エージェントは `~/.claude/projects/` にある過去の会話ログを読み、関連する PR や issue も調べます。返事は次の形です。

- **Capsule.** 今の状況を 5 項目以内で。
- **Threads.** 作業の筋ごとに、`[open PR #N]` や `[in flight <branch>]` などの状態付きで。
- **Problems.** 繰り返し出ている問題。
- **Next move.** 次にすること 1 つ。

### 11. プロトタイプで案を比べる

最初に出てきた設計をそのまま採用しないことが、Pt. 2 の要点の 1 つです。

```
/poteto-mode <機能> の案をいくつかプロトタイプして。/verify-<app> で動画かスクリーンショットを撮って、比べて選べるようにして
```

エージェントは **Prototype** playbook に従います。本番のコードとは別の作業用ディレクトリに、使い捨ての試作を作ります。UI なら、複数の案を切り替えボタン 1 つで見比べられるようにします。

返事には、試した案、案ごとの証拠、比較、おすすめが入っています。プロトタイプは捨てるものだ、とも書かれています。選んだ案の本番実装は、手順 4 のように Feature として頼みます。

### 12. `/architect` で設計する

関数の境界をまたぐような変更は、`/architect` で設計してから作ります。Pt. 2 の例 2 のプロンプトです。

```
/poteto-mode <機能> を作りたい。まず /architect で設計して、未解決の問いにはプロトタイプで答えて。実装に入る前に見せて
```

`/architect` は 5 つの段階で進みます。

1. **Ground.** `/how` と `/why` で、関係するシステムを調べます。
2. **Sketch.** 複数のモデル(opus、fable、sonnet)が、それぞれ別に設計案を出します。案は呼び出し側のコード例、型、関数のシグネチャ、根拠でできています。構造の違う案が最低 2 つ必要です。
3. **Agree.** 最後に「実装に入る前に見せて」と書いたので、ここで止まって案を見せます。
4. **Implement.** 了承すると、スケッチに沿って中身を書きます。
5. **Scrap.** 同じ種類の回避策があちこちに出たり、型に `any` やキャストが要ったりしたら、スケッチを捨てて設計し直します。

Claude Code 版では、案を出すのはすべて Claude のモデルです。Cursor 版のように別の会社のモデルは混ざらないので、案の幅はやや狭くなります。

### 13. README から先に書く

人に使ってもらうコードは、実装の前に使い方の文書を書くと形が見えます。作者は、社内フレームワーク Dune をチュートリアルから書き始めました。そのために作ったのが `/technical-writing` です。

```
/technical-writing <機能> を使う人向けのチュートリアルを書いて。実装はまだしない
```

返ってくる文書は、Diátaxis の 4 つの型のうち tutorial だけで書かれています。手順ごとに、読者に何が見えるかが書いてあります。この文書が、実装を確かめる目標になります。このチュートリアルも同じスキルで書きました。

### 14. 設計を計画にする

設計が決まったら、実行する計画にします。

```
/poteto-mode この設計を計画にして
```

エージェントは **Multi-phase plan** playbook に従います。PR ごとに節があり、どの箱にも「何が証拠になれば済みか」が書かれた計画ファイルができます。どの PR にも、実際にアプリを動かして確かめる手順が入っています。テストが通るだけでは済みにしない、というのがこの playbook の決まりです。

計画ができたら、エージェントは止まります。実行は、あなたが「進めて」と言ってからです。

## 第 3 部: エージェントを信頼できる環境を作る

講演の主張は、同時に動かすエージェントの数は、エージェントの仕事をどれだけ信頼できるかで決まる、というものです。信頼がないまま数を増やすと、質の低い PR と不具合が増えます。

### 15. 直した間違いを構造に残す

ここまでの手順で、エージェントの間違いを一度は直したはずです。その間違いが二度と起きないようにします。

```
/poteto-mode さっき私が直した <間違い> が、二度と起きないようにして。まずコードの構造で起こりえなくできるかを考え、無理なら lint か CI で止めて。ルールやスキルに書くのは最後の手段にする
```

講演では、再発を防ぐ場所を強い順に 4 つ挙げています。

1. コードの構造やデータ構造。間違いが書けないようにします。
2. 静的解析。lint、コンパイラ、CI です。
3. ルールやスキル。守られないこともあります。
4. スタイルガイド。人のレビューでしか守られません。

エージェントは既存のコードの形をまねします。回避策を 1 つ残すと、数週間でリポジトリ中に広がります。だから、間違いは見つけたときに構造で止めます。

### 16. コメントを疑う

講演では、エージェントのコメントが回避策の言い訳になる例を挙げています。作者のフレームワーク Dune では、コメントを禁止しました。

```
/no-comments
```

`comment-sicko` エージェントが、今のブランチの差分からコメントを 1 つずつ調べます。消すべきコメントは消し、コメントで隠していた回避策は根本から直します。残すコメントには、残す理由が付きます。

## 持ち帰るプロンプト

Pt. 2 の最後にある例を、そのまま使える形でまとめます。

原因の分からない不具合を調べる:

```
/poteto-mode バックグラウンドのワーカーがときどきタイムアウトで失敗する原因を調べて。分かっていること、使ったデータ、有力な仮説をまとめて
```

新しい境界を設計する:

```
/poteto-mode 外部 webhook にレート制限を入れたい。まず /architect で設計して、未解決の問いにはプロトタイプで答えて。進める前に見せて
```

大きな移行を小さな PR に分ける:

```
/poteto-mode UI ライブラリ全体を StyleX に移す計画を立てて。検証できる小さな PR に分けて、PR ごとに見た目の回帰テストと実機での確認手順を付ける。最終結果は元と完全に同じにする。バグも含めて
```

Slack で報告された問題を直す:

```
/poteto-mode /verify-<app> でこれを再現して。main で再現したら直して、証拠として動画を見せて
```

多くの場合、`/poteto-mode` とだけ書けば足ります。`/how` や `/architect` などは、`/poteto-mode` が必要に応じて自分で呼びます。

## 片付ける

練習用のブランチを消します。検証スキルを残したい場合は、`.claude/skills/verify-<app>/` だけを別のブランチに移して PR にします。

```bash
git switch main
git branch -D pstack-tutorial
```

## Cursor 版との違い

記事は Cursor と Grok Bot での使い方を書いています。Claude Code 版では次の点が違います。

- `/poteto-mode` は Cursor の Custom Mode のように固定できません。新しい作業を頼むたびに付けます。
- クラウドエージェントはありません。`/swarm` などの並列作業は、手元の worktree で動きます。
- Grok Bot のルーティンや Cursor の Automations はありません。定期実行は別の仕組みで組みます。

詳しくは [`claude-code.md`](../claude-code.md) にあります。スキル同士の関係は [スキル地図](skill-map.ja.md) にあります。
