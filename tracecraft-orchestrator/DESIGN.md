# Tracecraft リスク分析オーケストレーション層 設計

pstack `/architect` で作った設計。型と関数の形だけを `sketch/` に置いた(中身は `not implemented`)。`tsc --strict` は通る。

## 問題

Tracecraft で出した多層サプライチェーン分析(グラフ)がすでにある。ただし二次以降の取引先は貿易統計からの推定で、確度を持っている。「コバルトの UFLPA リスクは」「サプライヤー X の DRC 拠点が止まったら」「新疆は」のような問いに答えたい。答えるには、別チームが持つ分析モジュール(包括的な規制情報収集、調達リスク分析、今後はコスト影響シミュレーションや衛星森林破壊評価も)を呼び分ける。

形が自明でない理由は 5 つある。

- 1 回の分析に数時間とお金がかかる。LLM のツール呼び出しの中で待てないし、無駄な重複実行は実害になる。
- 結果を見てから次を決め直す必要がある(規制スキャンで新疆のポリシリコンが引っかかったら、その上流の三次精錬所を掘る)。
- 「コバルト」「DRC」といった言葉を、確度付きのグラフのノード集合に落とす必要がある。
- モジュールは増えていき、入力の単位も出力形式も違う。
- 報告の各記述を、どのモジュール実行・どのデータ版・どの確度から来たかまで辿れる必要がある。

## 使い方(呼び出し側から見た形)

```ts
const orch = createOrchestrator({
  store: pgEventStore(pool), wake: pgBossQueue(pool), graph: tracecraftGraph(api),
  modules: [regulatoryIntel, procurementRisk],        // モジュールを足す = アダプタを足す
  judgment: { planModel: "<Claude model id>", reportModel: "<Claude model id>", maxFindingsInDigest: 200 },
});

// Web 画面: 問いを受けたらすぐ ID を返す
const id = await orch.open({
  requestId: req.headers["idempotency-key"],          // 二重送信しても同じ ID
  companyId, requestedBy: user,
  question: "EV バッテリーのコバルトは UFLPA と EU のデューデリ規制にどれだけさらされているか",
  budget: { maxCostUsd: 20000, autoApprove: { belowCostUsd: 2000, belowHoursP90: 6 }, maxWaves: 3 },
});

// 数時間後: 状態画面や Slack ボット
const v = await orch.view(id);
// v.status === "awaiting_human"
// v.waitingOn[0] = { kind: "approval", launches: [{ module: "procurement-risk",
//   scope: "新疆の三次ポリシリコン精錬所 3 社(推定)", estimate: {hoursP50: 12, hoursP90: 18, costUsd: 9000},
//   why: "規制スキャンで CN/2804.61 が UFLPA 高リスク" }], ... }
// v.findings = 届いた分の知見(出典と確度つき)
await orch.send(id, { kind: "approve", inputId, approvalId: v.waitingOn[0].approvalId, by: user });

// 追加の問い、監視アラートからの起動、ワーカー
await orch.send(id, { kind: "follow_up", inputId, question: "同じ精錬所のリチウムも", by: user });
await orch.open({ requestId: `alert:${alert.id}`, trigger: { kind: "monitor", alertId: alert.id }, ... });
await orch.runWorker(signal);                                   // N 台で動かしてよい
app.post("/hooks/modules/:id", r => orch.ingestModuleCallback(r.params.id, r.body));
```

呼び出し側が触るのは `open` / `view` / `send` / `runWorker` / `ingestModuleCallback` の 5 つと、人の入力をまとめた `HumanInput` 型だけ。イベントログ、実行台帳、プロンプト、モジュールのワイヤ形式は見えない。モジュール側のチームが書くのは `ModuleAdapter` 1 つ。

## 形

ファイル構成(呼び出しの連鎖は最長で runtime → investigation(純関数) → modules / judgment):

| ファイル | 役割 |
|---|---|
| `index.ts` | 公開 API |
| `domain.ts` | 共通の型。ID、グラフのノード、`InputVersions`、`Finding`、`Claim`、イベント |
| `scope.ts` | 対象範囲の小さな言語 `ScopeExpr` と、グラフに対する決定的な解決 |
| `modules.ts` | `ModuleAdapter` 契約と、全調査で共有する実行台帳 `RunLedger` |
| `investigation.ts` | 純粋な判定 `evolve` / `decide` と費用ゲート |
| `judgment.ts` | LLM を使う 2 か所(計画、報告) |
| `runtime.ts` | I/O だけの薄い外殻 |

**データ構造**

1. **調査ごとの追記専用イベントログ。** 調査の状態として保存するのはこれだけ。状態、承認待ち、使った費用はすべてログからの導出で、別に保存しない(真実は 1 か所)。LLM の出力もイベントとして残すので、再起動しても LLM をもう一度呼ぶことはない。
2. **「アトム」単位の実行台帳。** アトムはモジュールの自然な仕事の単位。規制モジュールなら(国, HS コード)、調達リスクならサプライヤーのノード。キーは `hash(モジュール, 版, アトム, 入力の版)`。「コバルト」と「DRC」はどちらも (CD, 8105.20) に落ちるので、後から来た問いはただで結果を得る。入力の版には、モジュールが依存するデータセットの版と、グラフに依存する場合だけ(会社, グラフ版)を入れる。版が変われば自然にキャッシュを外れるので、古い結果は混ざらない。グラフに依存しないアトム(規制情報)は会社をまたいで共有され、依存するものは会社ごとに分かれる。
3. **`Finding`。** モジュール・計画役・報告のあいだで通じる唯一の出力型。対象ノード、観点、深刻度、名前付きの数値(`metrics`)、次の調査の手がかり(`leads`)、出典を持つ。確度は「モジュールの確度 × 対象ノードの確度の最小値」で計算するので、推定の層の不確かさがそのまま各知見に乗る。
4. **`ResolvedScope`。** `scope.resolve()` でしか作れない型。グラフの版に固定されたノードと確度の組。LLM はノード ID を書かない。`ScopeExpr`(`material` / `supplier` / `region` / `fromFindings` / `expand` / `intersect` / `union` / `minConfidence`)で言い、決定的なコードが解決する。曖昧なら人への確認に、空なら却下された手順になる。

**流れ。** `open` / `send` はイベントを足して起床を積む。ワーカーの 1 回の起床は、リースを取る → ログを畳む → 台帳から終わったアトムを取り込む → `decide(state)`(純関数)が効果を返す → 実行してイベントを足す、の順。効果は `plan` / `start` / `release` / `notify` / `synthesize` の 5 種で、どれも決まったキーを持ち、外部呼び出しはそのキーで冪等になる。途中で落ちても「畳み直して同じ効果を出し直す」だけで済む(per make-operations-idempotent)。モジュールのポーリングは調査ではなく **実行(launch)ごと** の起床が受け持つ。起動した調査が取り消されても、同じ実行を待つ他の調査は取り残されない。

**エージェントらしさは「波」で出す。** 1 回の計画呼び出しが見るのは、問い、モジュールの説明カード、グラフの概略、これまでの知見と手がかり、済んだ範囲、前の波で却下された理由。返すのは `{steps, done}`。波のアトムが全部そろったら、`done` か上限に達していない限り次の波を計画する。三次精錬所への深掘りは 2 つ目の波の `{ expand: { fromFindings: [f] }, direction: "upstream", tiers: 1 }` になる。

**LLM を使うのは 2 か所だけ**(`judgment.ts`): 次の波の計画と、報告の文章。範囲の解決、アトム化、重複排除、費用ゲート、確度、そして **報告に出る数字はすべて** 決定的なコードが扱う。報告の文は `{{placeholder}}` を使ったテンプレートで、数字は `Finding.metrics` から差し込む。裸の数字、存在しない出典、存在しない指標を含む文は `validateClaims` が落とす。`Claim.cites` は空にできない型。

**共有状態。** 調査をまたいで共有するのは台帳だけ。書くのは「挿入(なければ)」する起動側と、1 度だけ条件付き更新する確定側。ほかの調査のログには誰も書かない。各調査は自分の起床時に台帳を読んで取り込む(per separate-before-serializing-shared-state)。同じアトムが実行中なら、新しく起動せずその実行に相乗りする。最後の購読者が抜けた実行は `adapter.cancel` で止める。

**境界での検証**(per boundary-discipline): グラフは `scope.loadSnapshot`、モジュール出力は `adapter.toFindings`、LLM 出力はスキーマ・モジュール登録・`acceptsNodeKinds`・範囲解決、HTTP は `ingestModuleCallback` で検証する。内側は型を信じる。

**インターフェースの深さ。** 公開面は 5 メソッドと 1 つのユニオン型。その裏に、永続化と再開、再計画、不確かなグラフ上の範囲解決、調査をまたぐ重複排除と相乗り、費用ゲート、承認、出典管理、数字の捏造防止を隠している。`ModuleAdapter`(`project` / `estimate` / `launch` / `poll` / `toFindings` など)はわざと広い。どれもモジュールのチームしか知らない知識で、オーケストレーションの事情は入っていない。

**やらないこと:** 汎用の DAG やワークフローエンジン、波の中の手順間の依存関係、LLM による支出判断、モジュール結果の途中ストリーミング。

## 統合の判断

3 つのモデルに別々に設計させ(候補 1 = opus、候補 2 = fable、候補 3 = sonnet)、別の fable を審査役にした。3 案とも「追記専用イベントログ + 共有実行台帳 + モジュールアダプタ + LLM は状態を持たない判断関数」に収束した。この骨格は合意とみなしてよい。

- **土台: 候補 1。** 審査役も同じ判断で、6 項目すべてで最高点だった。決め手は、重複排除を問いや範囲ではなくアトムで行うこと、報告の数字を LLM に書かせないこと、`ScopeExpr` で LLM にノード ID を書かせないこと。
- **候補 2 から移植したもの:**
  - 見積もりを時間だけでなく `RunEstimate {hoursP50, hoursP90, costUsd}` にし、予算と自動承認を金額と時間の両方で判定する。
  - モジュールカードの `acceptsNodeKinds` で、合わないノード種への実行を決定的に却下する。
  - 計画呼び出しの監査記録 `PlannerTrace`(モデル、プロンプトのハッシュ、生出力、トークン数)。
  - 購読者のいなくなった実行を止める `adapter.cancel`。
- **候補 3 から移植したもの:** 曖昧さを人に確認するとき、「言葉の一致度」(`matchScore`)と「ノード自体の推定確度」を分けて見せる。
- **審査で見つかった候補 1 の不具合の修正:**
  - ポーリングを調査の効果から実行ごとの起床に移した。起動元の調査が取り消されても、相乗りしている調査が止まらない。
  - `domain.ts` が `index.ts` / `judgment.ts` を参照していた循環をなくした(入力型と計画の型を `domain.ts` へ移動)。
- **統合時に自分で直したもの:** 候補 1 はアトムのキーに常にグラフ版を入れていた。これだと規制情報のような、グラフに依存しない結果まで会社ごと・版ごとに作り直すことになる。グラフへの依存はアダプタが申告する形に変えた。依存する場合は会社 ID も入るので、他社のデータ由来の結果は混ざらない。
- **採らなかったもの:**
  - 候補 2 の「(モジュール, 範囲) をキーにした台帳」。部分集合を再利用できない。
  - 候補 2 の「曖昧な一致をそのまま含める」。違う会社に数時間を使う恐れがある。
  - 候補 3 の「LLM が承認の要否を決める」「読むたびに報告を LLM で作り直す」。支出と読み取りに LLM を入れない。
  - 候補 3 の「合成器がモジュール固有の抽出をする」。モジュールを足すたびに合成器の修正が要る。

## 受け入れたトレードオフ

- 波の単位で再計画するので、早く出た重大な知見も波がそろうまで待つ。その代わり、LLM 呼び出しの数に上限があり、承認は波ごとに 1 回で済み、判定は純関数のまま保てる。
- アダプタに結果をアトムごとに振り分けてもらう手間を受け入れる。その代わり、問いをまたいだ細かい再利用ができる。振り分けられないモジュールは 1 実行 = 1 アトムにすればよく、失うのは部分的な再利用だけ。
- 起床のたびにログを畳む。その代わり、落ちても安全で、監査記録が残り、LLM なしで再生できる。ログは数十〜数百件なのでスナップショットは要らない。
- 調査はグラフを `opened` 時点の版に固定する。その代わり、1 つの調査の中で範囲がぶれない。新しい版を使うには、追加の問いか新しい調査にする。
- 承認は実行ごとではなく波ごと。その代わり、中断が少ない。一部だけ承認したいときは、却下してから範囲を絞った追加の問いを出す。
- 通知は少なくとも 1 回(重複あり)。その代わり、送信の二重防止の仕組み(outbox)が要らない。
- 数字をプレースホルダにするので、文章が少し硬くなる。その代わり、法務や経営層に出す数字を LLM が捏造できない。

## 検討した別の形

- **長時間動くツール使用エージェントを Temporal / Inngest の上で動かす。** 計画が会話ログの中に暗黙に埋もれる。重複排除がプロンプトや散らばったコードに入り、数時間の待ちで履歴も文脈も膨らむ。見える構造が少なく、隠す方針も少ない。ただし `runtime.ts` の下の実行基盤としては使える(判定は基盤に依存しない)。
- **最初に問いを静的な DAG に変換して実行する。** 結果が出てから初めて分かる手がかりを掘れない。ここでは「最初の波」がこれに当たり、2 つ目以降の波を足した形になっている。
- **(モジュール, 解決済み範囲) で重複排除する。** 「コバルト」と「DRC」が仕事を共有できず、後から網羅状況の索引を足すことになる。これは「索引は後で足す」という、構造が間違っているときの兆候。
- **複数プロセスが書き込む共有ドキュメント(黒板)。** ロックとマージ規則が要る。「ストリームごとに書き手 1 つ + 台帳は読む側で合流」に置き換えた。

## 未決事項とリスク

- 既存のモジュールは冪等キーとアトムのまとめ投入を受け付けられるか。無理なら、アダプタに `launchId → 外部ジョブ ID` の対応表を持たせてよいか。
- モジュールの出力は(国, HS)やサプライヤーの単位に振り分けられるか。本質的に入力全体でしか動かないモジュールはどれか。
- 規制情報の「同じ入力の版」とは何か。データセットの版を出せるか、`maxAgeDays` だけに頼るか。
- グラフは州・自治区のような国より細かい位置(新疆など)を持っているか。国単位しかなければ、UFLPA の範囲は国全体になる。
- 調達・法務の利用者にとって、承認は波ごとで十分か。モジュールごとの費用を見せて実行ごとに承認したいか。
- 規制情報のアトムを会社間で共有するのは契約上問題ないか。問題があるなら、全アトムのキーに会社 ID を入れる(再利用は減る)。
- 計画の質は、モジュールの説明カードとグラフの概略に左右される。モジュールを足すとき、「問いと期待する手順」の小さな評価セットを必須にするか。

## 次の実装の一歩

`investigation.ts` の `evolve` / `decide` / `gate` を純関数として実装する。偽のアダプタを使い、イベント列の表形式テストを書く。対象は、自動承認の経路、承認の経路、再利用だけの波、落ちた後の出し直し、追加の問いによる再開、取り消し時の相乗り継続。I/O はまだ作らない。
